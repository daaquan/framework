- **Project:** framework
- **Description:** Phare is a lightweight PHP framework built on the [Phalcon](https://phalcon.io/) C extension.
- **Audit pattern — contract leak severity ranking:** when a `Contracts/*` interface itself `extends` a `Phalcon\…` interface, that is a HIGHER-severity leak than a concrete class extending one — the Phalcon type is baked into the *published contract*. Cross-ref `Contracts\Http\Kernel` (US-A02), `Contracts\Http\Response` (US-A05), `Eloquent\BuilderInterface` (US-B02). Distinguish from `Eloquent\ModelInterface` (US-B01) — stub interface Model doesn't implement = LOW severity (no real contract).
- **Audit pattern — "same name, opposite shape" porting hazards (running list):** `Model::create()` (B01 instance bool vs Laravel static returns Model), `Builder::paginate($page,$limit)` (B02 inverted arg order, returns Builder vs LengthAwarePaginator), `Migrator::rollback($steps)` (B05 positional int = batch-count vs Laravel options-array `['step'=>n]` counting migrations), `Factory::for(string)` (B06 SETS model vs Laravel parent-belongsTo), `LengthAwarePaginator::simplePaginate(): string` (B07 a paginator render method vs Laravel a Builder method returning a Paginator), `Authenticatable::getAuthIdentifierName`/`getAuthPasswordName` (C01 static vs Laravel instance), `Phare\Auth\Manager::login(User): bool` (C02 vs Laravel `SessionGuard::login(...): void`). Worth a dedicated section in the US-S01 synthesis.
- **Audit pattern — orphaned/unwired subsystem (NEW defect class, B07):** a subsystem can be present, well-shaped, and Phalcon-clean yet produce ZERO runtime value because nothing CONSTRUCTS it. Pagination's 5 classes are never instantiated by the ORM (`Builder::paginate` returns the Builder, not a paginator; no `simplePaginate`/`cursorPaginate`); `UrlWindow` is shipped but never called. Always grep `src/Phare/` for the PRODUCER (`grep -rn "new <Class>" src/Phare/`), not just the class definition. Distinct from stub-defect (a method that no-ops) — here whole classes are dead. Flag as its own US-S01 category.
- **Audit pattern — Phalcon-clean has two grades:** namespace-clean-but-rides-an-inherited-leak (B04 SoftDeletes rode the B02 Builder leak) vs fully-clean in namespace AND inheritance (B07 Pagination never touches Builder/Model/AbstractPdo). State which when claiming clean. Each clean subsystem has a "closest-to-parity" file: B05 `ForeignKeyDefinition`, B07 `Cursor` (1:1 with Laravel).
- **Audit pattern — diff Laravel from the ABSTRACTS, not the concretes:** the real paginator surface lives in `AbstractPaginator` (53 pub: ArrayAccess `offset*`, `toHtml`, `__call` ForwardsCalls, `useTailwind`/`useBootstrap*` view plumbing) + `AbstractCursorPaginator` (39); the concrete `Paginator`/`LengthAwarePaginator`/`CursorPaginator` add only ~10 each. Same trap as B02 Builder (BuildsQueries trait + `$passthru`). Enumerating only concretes under-counts Laravel by ~50 methods.
- **Audit pattern — no-contracts is Area-wide:** subsystems publish no `Contracts/*` interface yet name-match Laravel's contract methods — Validation (A06), View (A07), Pagination (B07, no `Contracts\Pagination\*`). Record as type-mismatch (undeclared contract), not missing-method.
- **Audit pattern — Phalcon-leak SHAPES (rank for §2):** (1) inheritance leak (`extends Phalcon\…` — B01 Model, B02 Builder, B03 Relation); (2) contract leak (`Contracts/* extends Phalcon\…` — A02/A05/B02, highest); (3) signature/union-return leak (B03 `hasOne(): …|Phalcon\…\Relation`); (4) **dependency/param leak** (B05 — class is Phalcon-clean by inheritance but a public ctor/param takes raw `\Phalcon\Db\Adapter\Pdo\AbstractPdo`: `Blueprint::toSql`, `SchemaBuilder::__construct`, `Grammar::compileBlueprint`, `Migrator::__construct`; no Phare `Connection` wrapper exists). Fix for (4) = wrap the connection (shared DB-layer work), not local.
- **Audit pattern — silent event-bypass defects** (distinct class from stub-defects): `Builder::update()` (B02 raw UPDATE SQL skips model events/mutators), Model `castAttribute` not invoking custom CastsAttributes contract (B01). When auditing a write/query path, check whether mutators + events fire.
- **Laravel Eloquent Builder real surface** = 93 public methods + 33-entry `$passthru` table forwarding to Query Builder (228 methods) + `BuildsQueries` trait + `QueriesRelationships` trait + `Macroable`. Enumerate ALL when diffing a facade-over-query subsystem.
- **Audit pattern — logout blast-radius defect class (C02, NEW):** `Phare\Auth\Manager::logout()` calls `$this->session->destroy()` (full-session wipe) where Laravel calls `$session->remove($this->getName())` (only the auth key). Distinct from stub-defect / silent-event-bypass / hardcoded-output families — this is "intent-correct, scope-incorrect" (destroy-when-you-meant-remove-one-key). Watch for analogous patterns: `cache->flush()` vs `cache->forget()`, `session->clear()` vs `session->remove()`. When auditing any "log out / clear / reset" method, check whether it nukes adjacent state.
- **Audit pattern — security-relevant implicit defaults (C02):** `Phalcon\Session\Manager::regenerateId(bool $deleteOldSession = true)` defaults to deleting the old session entry — security-sensitive. Phare's `Manager::regenerateSessionId()` relies on the implicit default. Flag any time a security-relevant method is called with no explicit args (session-fixation, password hashing, CSRF token rotation, cookie SameSite/HttpOnly). Implicit defaults can flip between vendor versions.
- **Audit pattern — wiring divergence at the container-binding level (C02):** Phare binds `session` (single SessionManager from SessionProvider) AND `session.manager` (SessionStoreManager registry) to DIFFERENT instances. Laravel: `session` IS the manager, one instance graph. SEPARATE defect class from missing-methods — record at the binding level. Grep `singleton\('[a-z]+\.manager'` to find more (cache.manager, queue.manager, broadcast.manager all have this shape).
- **Audit pattern — session-key isolation:** Laravel uses `'login_'.$name.'_'.sha1(static::class)` so guards are collision-safe by construction. Phare uses a single config value (`auth.session_id` fallback `"auth.{name}"`) — if globally set, all guards share one key. When auditing multi-X subsystems (multi-guard, multi-store, multi-connection), check whether keys are per-class-derived or config-driven. Config-driven = silent collision risk.
- **Audit pattern — count from STARTING CLASS not contract (C02):** Laravel `Contracts\Session\Session` = 26 methods; concrete `Illuminate\Session\Store` = 54. Apps consume the concrete (flash/increment/push/cache). Always diff concrete, not interface. Same trap as B02 Builder ($passthru), B07 Pagination (AbstractPaginator), C01 SessionGuard (GuardHelpers trait).
- **Audit pattern — Phare contract-leak inventory (C02 expanded):** subsystems where `Phare\Contracts\*` extends a Phalcon interface: `Contracts\Http\Kernel` (A02), `Contracts\Http\Response` (A05), `Contracts\Http\Request` (A04), `Eloquent\BuilderInterface` (B02), `Contracts\Session\Session` (C02). When US-S01 enumerates leaks, run `grep -rln 'extends \\\\?Phalcon\\\\' src/Phare/Contracts/` for the canonical list.
- **Audit pattern — provider-boundary contract-coupling leak (C03 confirmed 4×):** when a subsystem namespace is Phalcon-CLEAN, the leak is almost always in `src/Phare/Providers/<Subsystem>ServiceProvider.php` — shape is `implements Phalcon\Di\ServiceProviderInterface` + `register(Application|DiInterface $app)`. Confirmed at A07 BladeViewProvider, C01 AuthServiceProvider, C02 SessionProvider, C03 HashServiceProvider. After auditing a clean namespace, ALWAYS open the provider file before claiming "clean overall".
- **Audit pattern — silent-config-dropthrough defect class (C03, NEW):** a `createXxxDriver()` factory that does `new Driver()` with hard-coded `[]` options array, never reading `config('<subsystem>.<driver>')`. Phare `HashManager::createBcryptDriver` ignores `config('hashing.bcrypt')` entirely — `hashing.bcrypt.rounds`, `hashing.argon.memory`, etc. are silently ignored. Different shape from B03 silent-arg-drop (which drops a method arg). Watch for this in any Phare manager. Companion fact: Phare ships no `config/hashing.php`, no `config/session.php`, etc. — config-driven tuning is a synthesis cross-cut.
- **Audit pattern — infinite-rehash loop defect (C03, NEW):** `needsRehash` compares hasher options against the configured cost. If the hasher applies a runtime override (e.g. sodium Argon backend forces `threads=1`) but `needsRehash` still reads the configured `threads=2`, `needsRehash` returns `true` on every login and the app silently re-hashes forever. Only surfaces on PHP builds with `PASSWORD_ARGON2_PROVIDER === 'sodium'` — CI on libargon2 will miss it. Generalization: any time a runtime override flips a stored-vs-configured cost factor, `needsRehash`-style comparators are wrong. Same "config-vs-runtime-mismatch" shape as C02 §3 (session-key collision) but on hashing.
- **Audit pattern — `#[\SensitiveParameter]` is a Laravel signal (C03):** Laravel marks every password / secret parameter with `#[\SensitiveParameter]` so the value is redacted from stack traces / exception messages / error-handler payloads. Phare marks NONE — `grep -rln '#\[\\\\SensitiveParameter\]' src/Phare/` returns zero matches. When auditing a password/secret API (C03 Hashing, C04 Encrypter, C05 CSRF, C07 Password Reset), record the missing annotation as a security defect family — distinct from missing-method, this is missing-attribute. Cheap to add (1 token per param), high security value.
- **Audit pattern — security-defaults version drift (C03):** Laravel bumped `BcryptHasher::$rounds` default from 10 → 12 in Laravel 12.x (2025) — security hardening tied to compute-cost evolution. Phare still ships 10. When auditing security primitives, always cross-check: (a) the constant default IN the hasher class, (b) the config default in `config/<subsystem>.php`, (c) whether the config default is actually wired to the constructor. C03 fails (a) and (c).
- **Audit pattern — three-location subsystem (C03):** a subsystem can be split across 3 directories: `src/Phare/<Subsystem>/`, `src/Phare/Providers/<Subsystem>ServiceProvider.php`, AND `src/Phare/Container/Attributes/<X>.php`. C03 Hashing has all three. A07 Blade does not. Always grep `Container/Attributes/` for a subsystem-named attribute before claiming the audit is complete.

- **E01 design investigation (2026-05-29) — composition is tractable, not the feared XL:** `Container extends Phalcon\Di\Di` looked like all-providers/helpers/app blast radius, but measurement showed Phare ALREADY replaced Phalcon's resolution store with its own (`bindings`/`doMake`/`resolve`/`resolvedInstances`). `extends Di` buys only (a) ~5 internal store ops in `doMake()`/`resolveInstance()` (`get`/`getShared`/`set`/`getService`) + ONE `parent::has()` at `Container.php:1283`, and (b) type-identity as `DiInterface`. E01a = hold inner `Di` field + route those ops to it + `implements DiInterface` by delegating 14 methods (canonical list in `vendor/phalcon/ide-stubs/src/Di/DiInterface.php`). Behavior-preserving refactor; the 1326-test suite is the spec. Design doc: [[2026-05-29-e01-container-composition]].
- **E01b (full `implements DiInterface` removal) is GATED on B01:** `AbstractApplication extends Container extends Di` is passed into `Phalcon\Mvc\Micro`, and Eloquent Models extend `Phalcon\Mvc\Model` → ≈12 `setDI(DiInterface)`/`getDI()` sites in `Eloquent/Relations/*` + `Model.php`. Cannot drop the Phalcon type while a Phalcon C-class is the ORM base. So E01 splits: E01a (composition seam, shippable now) vs E01b (type removal, after B01 + app-core rework).
- **Provider migration is E02-remainder, NOT E01, and PHP forbids the naive fix:** the 27 `Providers/*ServiceProvider` `implements Phalcon\Di\ServiceProviderInterface` with `register(DiInterface $di)`. You CANNOT narrow that param to `register(ContractsContainer $app)` — fatal "Declaration must be compatible" (PHP allows param widening/contravariance only). Real fix = migrate each onto the already-shipped E02 base `Phare\Support\ServiceProvider` (`register(): void`, ctor-injected `Phare\Contracts\Foundation\Container`). The registration site `AbstractApplication::registerConfiguredProviders()` (`:305-326`) ALREADY dual-dispatches both conventions (`is_subclass_of(...Phare\Support\ServiceProvider)` vs Phalcon interface), so migration is per-file and incremental: `extends ServiceProvider`, `register(): void`, `$app`→`$this->app`, drop 3 Phalcon/Application imports.
