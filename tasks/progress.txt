# Ralph Progress — Laravel 13 Parity Audit Pass

## Codebase Patterns
- Audit PRD is READ-AND-RECORD ONLY. Never edit any file under `src/Phare/`. Output is docs only.
- Laravel 13 reference is read-only at `/opt/laravel-framework/src/Illuminate/` — confirmed version `13.2.0` (const VERSION in Foundation/Application.php).
- Each subsystem story appends a `### <Subsystem>` section to `docs/audit-area-{a..e}.md` in the fixed shape: `現状 (Current)` / `期待 (Expected)` / `差分 (Gaps)` / `工数感 (Effort: S|M|L)`.
- Gaps split into three categories: Missing / Type mismatch / Phalcon leak.
- Wrapper Rule (§2): a public method param/return of raw `Phalcon\*` type = a leak/gap. Container `get()/has()` inherited from `Phalcon\Di\Di` is a pre-documented exception, NOT a new gap.
- Effort rating is coarse S/M/L with a one-line rationale.
- Enumerate Laravel public methods fast: `grep -oE 'public function [a-zA-Z_]+\(' <file>` (avoid piping into RTK-hooked commands that choke on `--` flags; keep grep simple).
- Phare public APIs are frequently UNTYPED (no param/return types) — record that as a Type mismatch vs Laravel's typed signatures.
- The Ralph runner expects `tasks/prd.json`; it was generated from `tasks/prd-parity-audit-pass.md`. Branch: `ralph/parity-audit-pass`.
- Published-dependency Phalcon leak (a Phare class publishes a `Phalcon\*` type as a constructor/method parameter or property type, without inheriting from Phalcon) is now its OWN recurring leak class — distinct from inheritance-leak (B01/B02/B03) and contract-leak (A02/A05/B02). Instances: B05 schema (AbstractPdo), B06 seeders/factories (AbstractPdo), C01 session guard (ConfigInterface), C03 HashServiceProvider::register(Application|DiInterface). The fix shape is shared: introduce/use the Phare wrapper (Connection, Config\Repository, Foundation\Application-only public surface) and re-type the published surface.
- Provider-boundary contract-coupling leak (`implements Phalcon\Di\ServiceProviderInterface`) is the recurring shape for "subsystem-namespace Phalcon-clean, but its provider in `src/Phare/Providers/` is not". Confirmed at A07 BladeViewProvider, C01 AuthServiceProvider, C02 SessionProvider, C03 HashServiceProvider, C04 EncrypterProvider. Always open `src/Phare/Providers/<Subsystem>ServiceProvider.php` after auditing a clean namespace — that is where the leak typically hides.
- NEW leak class (C04): **DI-slot leak.** The leak IS the binding: a `singleton('<slot>', ...)` closure constructs a raw `Phalcon\*` class, regardless of whether a Phare-namespace wrapper exists. Distinct from inheritance / contract / published-dependency / provider-boundary leaks. Canonical example: `EncrypterProvider` binds `'encrypter'` to `Phalcon\Encryption\Crypt` while `Phare\Encryption\Encrypter` exists but is never wired. Future audits: do not stop at "is the Phare class clean?" — grep `singleton\('<slot>'` in `src/Phare/Providers/` AND inspect the closure body's `new ...` target. Also surfaces at C04 `'random'` (raw Phalcon Random) and `'security'` (raw Phalcon Security) bindings in the same provider.
- NEW leak class (C04): **Helper-return-type leak.** A global helper in `Phare\Support\helpers.php` publishes a `Phalcon\*` type in its return type. Canonical example: `function encrypter(): Crypt` — return type is `Phalcon\Encryption\Crypt`. Imports to grep at US-E06: `Phalcon\Config\Config`, `Phalcon\Di\Di`, `Phalcon\Encryption\Crypt`, `Phalcon\Support\Debug\Dump`, `Phalcon\Support\Helper\Str\Random` (all present in helpers.php today).
- **Dual-stack pattern** (NEW recurring shape, A07 → C04): the subsystem ships a Laravel-shaped Phare class AND a Phalcon-class binding in the same container slot. The Phalcon stack WINS at the slot; the Phare class is reduced to a dead-or-niche side path. Wire formats are typically INCOMPATIBLE. Confirmed: A07 BladeView (Phare\View dead stub + Phalcon BladeView wins), C04 Encrypter (Phare\Encryption\Encrypter wired ONLY by the encrypted-cast call site + Phalcon Crypt wins). Future audits: ask "what does `app('<slot>')` actually return?" — if the Phare class exists but is bypassed, log as dual-stack.
- Running list of same-name/opposite-shape porting hazards (for US-S01 synthesis): B01 `Model::create`, B02 `Builder::paginate`, B05 `Migrator::rollback`, B06 `Factory::for`, B07 `LengthAwarePaginator::simplePaginate`, C01 `Authenticatable::getAuthIdentifierName`/`getAuthPasswordName` (static-vs-instance), C02 `Manager::login(User): bool` (vs Laravel `SessionGuard::login(...): void`), C03 `HashManager::extend(Closure|HasherInterface)` (widens Laravel's Closure-only), C04 `Encrypter::generateKey($cipher)` (instance vs Laravel static).
- No-contracts pattern (Phare ships methods but no interface for them) is Area-wide. Confirmed: A06 Validation, A07 View, B06 Factories, B07 Pagination, C01 Auth Factory/Guard/StatefulGuard/UserProvider, C02 GuardHelpers (no `Contracts\Auth\Guard`/`StatefulGuard` for `Phare\Auth\Manager`), C03 Hashing (no `Contracts\Hashing\Hasher`; `HasherInterface` lives inside `Phare\Hashing\` namespace not `Phare\Contracts\Hashing\`), C04 Encryption (NO `Contracts\Encryption\Encrypter` AND NO `Contracts\Encryption\StringEncrypter`; `Phare\Encryption\Encrypter` implements nothing). Record as inherited type-mismatch, do not re-narrate per subsystem.
- NEW defect class for US-S01 synthesis (C04): **key-rotation unreachable** — `Phare\Encryption\Encrypter` has no `$previousKeys` field / `previousKeys()` setter / `getAllKeys()` / `getPreviousKeys()`, and `decrypt()` does not loop. An `APP_KEY` rotation in production strands every existing encrypted cell, encrypted cookie, and `Encryptable` queue payload. Distinct from C02 logout blast-radius (auth-side), C03 infinite-rehash loop (hash-side). Pattern note: any time Laravel exposes a "primary + previous" surface (encrypter keys, signing keys, JWT keys, broadcast auth signatures), grep Phare for the previous-values plumbing — Phare consistently drops it. Watch US-C05 (CSRF token rotation), US-C07 (password reset token rotation), US-D03 (broadcast auth signature rotation) for the same shape.
- NEW defect class for US-S01 synthesis (C04): **naming-defect family** — a helper or method whose NAME implies one operation but whose BODY does another. Canonical example: `Phare\Support\helpers.php::hash($value, $key)` returns `encrypter()->encryptBase64($value, $key)` — i.e. encrypted ciphertext, NOT a hash; ALSO collides with PHP's built-in `hash()`. Distinct from silent-config-dropthrough (which is a wiring defect — the function does what it says, just at hard-coded defaults) and stub-defect (which is a body that never runs). Future audits: when a helper short-circuits to another helper, verify the BODY matches the NAME.
- NEW defect class for US-S01 synthesis (C02): **logout blast-radius** — `Phare\Auth\Manager::logout()` calls `$this->session->destroy()` which wipes the ENTIRE session (CSRF token, flash data, previousUrl, every other session key) instead of the auth key only (Laravel: `$session->remove($this->getName())`). Distinct from stub-defect / silent-event-bypass / hardcoded-output families. Flag the **session-fixation mitigation gap** alongside: `login()` calls `regenerateId()` without the `deleteOldSession=true` flag.
- NEW defect class for US-S01 synthesis (C03): **silent-config-dropthrough** — driver factories `new BcryptHasher()` / `new ArgonHasher()` with hard-coded `[]` options array, never read `config('hashing.bcrypt')` / `config('hashing.argon')`. Same family as B03 BelongsToMany attach `$touch`. Distinct from stub-defect: code runs and stores hashes, just at the hard-coded defaults instead of the configured ones. Watch for this pattern in any Phare manager that has a `createXxxDriver` factory.
- NEW security-defect family for US-S01 synthesis (C03): (a) `#[\SensitiveParameter]` absent on every password/secret parameter — leaks plaintext into stack traces; (b) BcryptHasher default rounds=10 vs Laravel 12 (~4× weaker on fresh install); (c) `$verifyAlgorithm` field missing — cross-algorithm verify silently false-passes; (d) bcrypt 72-byte truncation undetectable (no `$limit`); (e) sodium-provider thread-count override missing — `needsRehash` returns true forever on sodium Argon builds (**infinite-rehash loop**). The infinite-rehash loop is the most severe — flag distinctly because it is a runtime-only defect that only appears when PHP is compiled with the sodium Argon backend; CI on the libargon2 backend will not catch it.

- Result: Effort L. NO JsonResponse, NO RedirectResponse, NO ResponseFactory.
- **Learnings for future iterations:**

  - `FileResponse`/`StreamedResponse` extend `Phalcon\Http\Response` directly (not Phare's `Response`) — a subsystem can have classes that bypass the project's own wrapper. Check the `extends` clause of every class, not just the primary one.

Naming-and-shape divergence at the binding level is a SEPARATE class from missing-methods — record explicitly. Same pattern recurs in cache/queue/broadcast — grep `singleton\('[a-z]+\.manager'` to find more.
  - **Session-key isolation gotcha:** Laravel hashes the guard class into the session key (`'login_'.$name.'_'.sha1(static::class)`) so different guards never collide; Phare uses a single config key (`auth.session_id` falling back to `"auth.{name}"`). If an app legacy-sets `auth.session_id`, all guards share one key. When auditing multi-guard subsystems always check whether keys are per-class-derived or config-driven — config-driven is a silent collision risk.
  - Enumerate Laravel guard surface from the STARTING-CLASS file: `grep -c '^\s*public function' Auth/SessionGuard.php` = 22 + `Auth/GuardHelpers.php` = 9 → ~31 publishable. Don't forget Macroable adds `macro`/`hasMacro`/`mixin`/`flushMacros` — and `SupportsBasicAuth` is empty (marker interface). The `__construct` counts as public but isn't a "method" in the diff sense.

- Diffed `src/Phare/Hashing/` (6 files) + `Providers/HashServiceProvider.php` + `Container/Attributes/Hash.php` vs Laravel 13 `Hashing/{HashManager,AbstractHasher,BcryptHasher,ArgonHasher,Argon2IdHasher,HashServiceProvider}` + `Contracts/Hashing/Hasher`.

- Result: Effort M. SMALLEST Area-C subsystem so far (6 source files, 8 own public manager methods, 4 hasher contract methods) but security-critical so M not S. Subsystem namespace `src/Phare/Hashing/` is **Phalcon-CLEAN** (zero `Phalcon\*` references). Leaks live entirely in the out-of-namespace `src/Phare/Providers/HashServiceProvider.php`: ➀ provider-boundary `implements Phalcon\Di\ServiceProviderInterface` (recurs A07/C01/C02 — now FOURTH consecutive subsystem with this exact shape); ➁ published-dependency `register(Application|DiInterface $app)` on `Phalcon\Di\DiInterface` (recurs B05/B06/C01). Security defect cluster (5): (1) default `BcryptHasher::$rounds=10` vs Laravel 12, (2) zero `#[\SensitiveParameter]` annotations, (3) no `$verifyAlgorithm` field on any hasher, (4) no bcrypt `$limit`/`InvalidArgumentException` for >72-byte values, (5) no sodium-provider thread-count override → **infinite-rehash loop** on sodium builds. Correctness defect: silent-config-dropthrough — driver factories `new BcryptHasher()` / `new ArgonHasher()` ignore `config('hashing.bcrypt')` / `config('hashing.argon')` entirely; no `config/hashing.php` ships in the framework. Same-name-different-shape porting hazard (8th): `HashManager::extend(Closure|HasherInterface)` WIDENS Laravel's Closure-only.
- **Learnings for future iterations:**
  - 4th consecutive subsystem confirms the pattern: **when the subsystem namespace is Phalcon-clean, always open `src/Phare/Providers/<Subsystem>ServiceProvider.php` next.** That is where the published Phalcon dependency hides (A07 BladeViewProvider, C01 AuthServiceProvider, C02 SessionProvider, C03 HashServiceProvider all share this exact shape: `implements Phalcon\Di\ServiceProviderInterface` + `register(Application|DiInterface)`). Promoted to a Codebase Pattern.
  - **NEW defect class — silent-config-dropthrough.** A driver factory that calls `new Hasher()` with hard-coded `[]` options is functionally identical to a stub-defect for config-driven tuning. Different from B03's silent-arg-drop (drops a method arg) — here the constructor itself never reads config. Watch for this in any `createXxxDriver()` method that doesn't pass `$this->config->get('xxx')` to the driver ctor.
  - **NEW defect class — infinite-rehash loop.** When the hasher stores `threads=1` (sodium-forced) but `needsRehash()` compares against the configured `threads=2`, `needsRehash` returns true on every login and the app re-hashes forever. CI on libargon2 (default PHP build) will not catch it — the bug only surfaces on PHP builds with `PASSWORD_ARGON2_PROVIDER === 'sodium'`. Same "config-vs-runtime-mismatch" shape as C02 §3 `auth.session_id` collision but on hashing.
  - **`#[\SensitiveParameter]` audit signal.** Laravel marks every `$value` on `make/check/isHashed`. Phare marks none. Grep `grep -rln '#\[\\\\SensitiveParameter\]' src/Phare/` returns ZERO matches → flag any future audit that touches a password/secret API to record this as a defect class. Future C04 Encrypter (US-C04) will hit this too.
  - **Bcrypt default-rounds drift.** Laravel bumped its default from 10 → 12 in Laravel 12.x (2025) — security hardening. Phare still ships 10. Watch for similar version-drift defaults: argon memory_cost, password_hash algorithm constants, openssl cipher. When auditing security primitives, ALWAYS check both the field default AND the config default, AND whether the config default is actually wired.
  - **HashManager.extend widening.** Phare accepts `Closure|HasherInterface` for backwards-compat. This is the third documented "Phare-widens-Laravel-contract" porting hazard (after B01 BuilderInterface contract widening + A02 union returns). When Phare→Laravel migration runs, all three need narrowing.
  - **Look in BOTH `src/Phare/<Subsystem>/` AND `src/Phare/Providers/<Subsystem>ServiceProvider.php` AND `src/Phare/Container/Attributes/<X>.php`.** C03 has its container attribute at `Container/Attributes/Hash.php` — a third location for subsystem code. Cross-reference for A07 (no attribute) vs C03 (has attribute) — pattern is "subsystems with container attributes get a 4th audit file".
  - The "hash.driver" missing binding has the same shape as C01's missing `auth.guard`/specific guard bindings — Phare's container has fewer-but-coarser bindings than Laravel's, by design. Always grep `singleton\('[subsystem]\.` in BOTH Phare and Laravel providers to enumerate the binding-graph gap.
