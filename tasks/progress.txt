# Ralph Progress — Laravel 13 Parity Audit Pass

## Codebase Patterns
- Audit PRD is READ-AND-RECORD ONLY. Never edit any file under `src/Phare/`. Output is docs only.
- Laravel 13 reference is read-only at `/opt/laravel-framework/src/Illuminate/` — confirmed version `13.2.0` (const VERSION in Foundation/Application.php).
- Each subsystem story appends a `### <Subsystem>` section to `docs/audit-area-{a..e}.md` in the fixed shape: `Current` / `Expected` / `Gaps` / `Effort: S|M|L`.
- Gaps split into three categories: Missing / Type mismatch / Phalcon leak.
- Wrapper Rule (§2): a public method param/return of raw `Phalcon\*` type = a leak/gap. Container `get()/has()` inherited from `Phalcon\Di\Di` is a pre-documented exception, NOT a new gap.
- Effort rating is coarse S/M/L with a one-line rationale.
- Enumerate Laravel public methods fast: `grep -oE 'public function [a-zA-Z_]+\(' <file>` (avoid piping into RTK-hooked commands that choke on `--` flags; keep grep simple).
- Phare public APIs are frequently UNTYPED (no param/return types) — record that as a Type mismatch vs Laravel's typed signatures.
- The Ralph runner expects `tasks/prd.json`; it was generated from `tasks/prd-parity-audit-pass.md`. Branch: `ralph/parity-audit-pass`.
- Published-dependency Phalcon leak (a Phare class publishes a `Phalcon\*` type as a constructor/method parameter or property type, without inheriting from Phalcon) is now its OWN recurring leak class — distinct from inheritance-leak (B01/B02/B03) and contract-leak (A02/A05/B02). Instances: B05 schema (AbstractPdo), B06 seeders/factories (AbstractPdo), C01 session guard (ConfigInterface), C03 HashServiceProvider::register(Application|DiInterface). The fix shape is shared: introduce/use the Phare wrapper (Connection, Config\Repository, Foundation\Application-only public surface) and re-type the published surface.
- Provider-boundary contract-coupling leak (`implements Phalcon\Di\ServiceProviderInterface`) is the recurring shape for "subsystem-namespace Phalcon-clean, but its provider in `src/Phare/Providers/` is not". Confirmed at A07 BladeViewProvider, C01 AuthServiceProvider, C02 SessionProvider, C03 HashServiceProvider, C04 EncrypterProvider. Always open `src/Phare/Providers/<Subsystem>ServiceProvider.php` after auditing a clean namespace — that is where the leak typically hides.
- NEW leak class (C04): **DI-slot leak.** The leak IS the binding: a `singleton('<slot>', ...)` closure constructs a raw `Phalcon\*` class, regardless of whether a Phare-namespace wrapper exists. Distinct from inheritance / contract / published-dependency / provider-boundary leaks. Canonical example: `EncrypterProvider` binds `'encrypter'` to `Phalcon\Encryption\Crypt` while `Phare\Encryption\Encrypter` exists but is never wired. Future audits: do not stop at "is the Phare class clean?" — grep `singleton\('<slot>'` in `src/Phare/Providers/` AND inspect the closure body's `new ...` target. Also surfaces at C04 `'random'` (raw Phalcon Random) and `'security'` (raw Phalcon Security) bindings in the same provider.
- NEW leak class (C04): **Helper-return-type leak.** A global helper in `Phare\Support\helpers.php` publishes a `Phalcon\*` type in its return type. Canonical example: `function encrypter(): Crypt` — return type is `Phalcon\Encryption\Crypt`. Imports to grep at US-E06: `Phalcon\Config\Config`, `Phalcon\Di\Di`, `Phalcon\Encryption\Crypt`, `Phalcon\Support\Debug\Dump`, `Phalcon\Support\Helper\Str\Random` (all present in helpers.php today).
- **Dual-stack pattern** (NEW recurring shape, A07 → C04): the subsystem ships a Laravel-shaped Phare class AND a Phalcon-class binding in the same container slot. The Phalcon stack WINS at the slot; the Phare class is reduced to a dead-or-niche side path. Wire formats are typically INCOMPATIBLE. Confirmed: A07 BladeView (Phare\View dead stub + Phalcon BladeView wins), C04 Encrypter (Phare\Encryption\Encrypter wired ONLY by the encrypted-cast call site + Phalcon Crypt wins). Future audits: ask "what does `app('<slot>')` actually return?" — if the Phare class exists but is bypassed, log as dual-stack.
- Running list of same-name/opposite-shape porting hazards (for US-S01 synthesis): B01 `Model::create`, B02 `Builder::paginate`, B05 `Migrator::rollback`, B06 `Factory::for`, B07 `LengthAwarePaginator::simplePaginate`, C01 `Authenticatable::getAuthIdentifierName`/`getAuthPasswordName` (static-vs-instance), C02 `Manager::login(User): bool` (vs Laravel `SessionGuard::login(...): void`), C03 `HashManager::extend(Closure|HasherInterface)` (widens Laravel's Closure-only), C04 `Encrypter::generateKey($cipher)` (instance vs Laravel static).
- No-contracts pattern (Phare ships methods but no interface for them) is Area-wide. Confirmed: A06 Validation, A07 View, B06 Factories, B07 Pagination, C01 Auth Factory/Guard/StatefulGuard/UserProvider, C02 GuardHelpers (no `Contracts\Auth\Guard`/`StatefulGuard` for `Phare\Auth\Manager`), C03 Hashing (no `Contracts\Hashing\Hasher`; `HasherInterface` lives inside `Phare\Hashing\` namespace not `Phare\Contracts\Hashing\`), C04 Encryption (NO `Contracts\Encryption\Encrypter` AND NO `Contracts\Encryption\StringEncrypter`; `Phare\Encryption\Encrypter` implements nothing). Record as inherited type-mismatch, do not re-narrate per subsystem.
- NEW defect class for US-S01 synthesis (C04): **key-rotation unreachable** — `Phare\Encryption\Encrypter` has no `$previousKeys` field / `previousKeys()` setter / `getAllKeys()` / `getPreviousKeys()`, and `decrypt()` does not loop. An `APP_KEY` rotation in production strands every existing encrypted cell, encrypted cookie, and `Encryptable` queue payload. Distinct from C02 logout blast-radius (auth-side), C03 infinite-rehash loop (hash-side). Pattern note: any time Laravel exposes a "primary + previous" surface (encrypter keys, signing keys, JWT keys, broadcast auth signatures), grep Phare for the previous-values plumbing — Phare consistently drops it. Watch US-C05 (CSRF token rotation), US-C07 (password reset token rotation), US-D03 (broadcast auth signature rotation) for the same shape.
- NEW defect class for US-S01 synthesis (C04): **naming-defect family** — a helper or method whose NAME implies one operation but whose BODY does another. Canonical example: `Phare\Support\helpers.php::hash($value, $key)` returns `encrypter()->encryptBase64($value, $key)` — i.e. encrypted ciphertext, NOT a hash; ALSO collides with PHP's built-in `hash()`. Distinct from silent-config-dropthrough (which is a wiring defect — the function does what it says, just at hard-coded defaults) and stub-defect (which is a body that never runs). Future audits: when a helper short-circuits to another helper, verify the BODY matches the NAME.
- NEW defect class for US-S01 synthesis (C02): **logout blast-radius** — `Phare\Auth\Manager::logout()` calls `$this->session->destroy()` which wipes the ENTIRE session (CSRF token, flash data, previousUrl, every other session key) instead of the auth key only (Laravel: `$session->remove($this->getName())`). Distinct from stub-defect / silent-event-bypass / hardcoded-output families. Flag the **session-fixation mitigation gap** alongside: `login()` calls `regenerateId()` without the `deleteOldSession=true` flag.
- NEW defect class for US-S01 synthesis (C03): **silent-config-dropthrough** — driver factories `new BcryptHasher()` / `new ArgonHasher()` with hard-coded `[]` options array, never read `config('hashing.bcrypt')` / `config('hashing.argon')`. Same family as B03 BelongsToMany attach `$touch`. Distinct from stub-defect: code runs and stores hashes, just at the hard-coded defaults instead of the configured ones. Watch for this pattern in any Phare manager that has a `createXxxDriver` factory.
- NEW security-defect family for US-S01 synthesis (C03): (a) `#[\SensitiveParameter]` absent on every password/secret parameter — leaks plaintext into stack traces; (b) BcryptHasher default rounds=10 vs Laravel 12 (~4× weaker on fresh install); (c) `$verifyAlgorithm` field missing — cross-algorithm verify silently false-passes; (d) bcrypt 72-byte truncation undetectable (no `$limit`); (e) sodium-provider thread-count override missing — `needsRehash` returns true forever on sodium Argon builds (**infinite-rehash loop**). The infinite-rehash loop is the most severe — flag distinctly because it is a runtime-only defect that only appears when PHP is compiled with the sodium Argon backend; CI on the libargon2 backend will not catch it.
- NEW pattern (C05): **Triple-stack** — the A07/C04 dual-stack defect class can extend to THREE concurrent stacks in one subsystem. Canonical CSRF instance: BladeOne (vendored EFTEC v4.9) writes `$_SESSION[$tokenId] = $token.'|'.$ipClient` via `getCsrfToken/regenerateToken` (Stack 3), `Phare\Security\Csrf` writes session key `_csrf_token` plain token via `app('session')->set(...)` (Stack 2), Laravel `Session\Store::token()` writes session key `_token` plain (Stack 1, target). Three writers, three formats, one session — a form roundtrip can silently false-fail when Blade `@csrf` and a Phare `Csrf::field()` render in the same view. Future audits: when a subsystem ships a Laravel-shaped class AND a Phalcon-equivalent binding AND a vendored engine carries its own subsystem-state, log as triple-stack.
- NEW pattern (C05): **Provider-boundary-leak NOT applicable.** The A07/C01/C02/C03/C04 streak of 5 consecutive subsystems with `Providers/<X>ServiceProvider.php implements Phalcon\Di\ServiceProviderInterface` ends at C05. CSRF has NO `CsrfServiceProvider.php` / `SecurityServiceProvider.php` — the middleware and `Csrf` helper are container-auto-resolved via constructor injection. Worth recording for US-S01: when a subsystem has no provider, the provider-boundary leak class is structurally inapplicable; check container auto-resolution targets instead (`grep "make(<Class>::class)"`).
- NEW defect class for US-S01 synthesis (C05): **CSRF token rotation unreachable.** Same family as C04 §1 (key-rotation unreachable) and C03 (e) infinite-rehash loop. `Phare\Security\Csrf::generateToken()` is only called from `getToken()` when the session key is missing; `Session\Store::regenerateToken()` does not exist (C02 §coverage 18/54); no Phare call site rotates the CSRF token on login / session->regenerate / privilege change. Once minted, the token lives forever in the session. Pattern note: token-rotation surfaces (CSRF, recaller, password-reset, broadcast-auth) are systematically dropped. Watch US-C07 (password-reset token expiry rotation), US-D03 (broadcast signature rotation) for the same shape.
- NEW silent-arg-drop instance (C05): `Phare\Middleware\VerifyCsrfToken::__construct(Application $app)` is 1 arg vs Laravel `PreventRequestForgery::__construct(Application $app, Encrypter $encrypter)`. Drops the encrypter dependency, which structurally disables decryption of the `X-XSRF-TOKEN` request header → Phare middleware reads the header as PLAINTEXT, making it wire-incompatible with Laravel SPAs (Axios/Inertia) that send the encrypted XSRF-TOKEN cookie value as the header. Running silent-arg-drop list (B02 update/B03 pivots/C01 attempt|login|loginUsingId $remember/C03 silent-config-dropthrough/C05 VerifyCsrfToken $encrypter) is now 5 instances across 4 areas — promote to a §2 leak-equivalent in US-S01 even though it isn't a Phalcon-leak by type.
- Running list of same-name/opposite-shape porting hazards is now 11 entries with C06 `RateLimiter::attempt`: Phare throws `TooManyRequestsException` on rejection vs Laravel returns `false`; arg order also inverted (Phare `$callback` LAST and optional, Laravel 3rd and required). B01 `Model::create`, B02 `Builder::paginate`, B05 `Migrator::rollback`, B06 `Factory::for`, B07 `LengthAwarePaginator::simplePaginate`, C01 `Authenticatable::getAuth*Name` (static-vs-instance), C02 `Manager::login`, C03 `HashManager::extend`, C04 `Encrypter::generateKey`, C05 `addExcept`/`except`, C06 `attempt`.
- NEW defect class for US-S01 synthesis (C06): **service-locator-over-DI** — a class takes `Phare\Contracts\Foundation\Application $app` then `$this->app->make('<slot>')`s the cache/db/queue/etc. inside its methods, instead of constructor-injecting the concrete contract (`Contracts\Cache\Repository`, etc.). Canonical example: `Phare\RateLimit\RateLimiter::__construct(Application $app)` + `protected function getCache() { return $this->app->make('cache'); }`. Distinct from published-dependency leak (which TYPES the wrong thing) and from DI-slot leak (which BINDS the wrong thing): here the dependency is HIDDEN entirely — invisible at typecheck, untestable without booting the container, latent DI-slot-leak risk if the bound class ever changes. Watch for this anywhere a class accepts `Application` instead of a domain-specific contract. Promoting to top-level US-S01 defect class.
- NEW defect class for US-S01 synthesis (C06): **silent unit-divergence.** A parameter or field uses the SAME name as Laravel but a DIFFERENT time unit. Canonical example: Phare `RateLimiter::attempt($key, $maxAttempts, int $decayMinutes=1, ...)` vs Laravel `attempt($key, $maxAttempts, Closure, int $decaySeconds=60)`; Phare `Limit::$decayMinutes` vs Laravel `Limit::$decaySeconds`; Phare `ThrottleRequests::handle(..., int $decayMinutes=1)` then `$limit->decayMinutes * 60` internally. A literal port `$limiter->attempt('foo', 5, 60, $cb)` means 60 MINUTES in Phare and 60 SECONDS in Laravel — silent 60× divergence undetectable without integration tests. Distinct from C03 silent-config-dropthrough (which silently uses defaults instead of config) — here a config value IS read, just multiplied by the wrong unit. Watch for the same shape on session timeouts (`config('session.lifetime')` minutes-vs-seconds), queue retry-after, password-reset TTL, JWT exp, signed-URL TTL. Promoting to top-level US-S01 defect class.
- NEW defect class for US-S01 synthesis (C06): **silent-reset on un-cleaned key.** `Phare\RateLimit\RateLimiter::tooManyAttempts` passes the raw `$key . ':timer'` to `$this->getCache()->has(...)` without calling `cleanRateLimiterKey()` first; same defect in `attempts`/`resetAttempts`/`remaining`/`clear`/`availableIn`. For any key containing HTML entities (e.g. user-controlled email `'a&b@c.com'` → htmlentities → `'a&amp;b@c.com'`), the timer-key read MISSES, the `>= $maxAttempts` branch silently calls `resetAttempts`, **the lockout fails AND the counter wipes** (fail-open AND wipe-history). Worse than B04's un-qualified-column (which errors loudly on joins). Same family as A04 Request input snapshot in `__construct` (correctness-without-error). Future audits: when a subsystem ships a `cleanXxxKey()`/`normalizeXxx()` helper, grep every public method and verify it's CALLED, not just defined.
- NEW pattern (C06): **service-locator + auto-resolved-singleton-instance-state-loss.** When a class with `protected array $limiters = []` (or similar mutable instance state) is bound NEITHER via `singleton()` NOR via a provider AND its ctor is just type-hinted `(Application $app)`, the container auto-resolves a NEW instance per call. Phare `RateLimiter` exemplifies: any `app('Phare\RateLimit\RateLimiter')->for('api', ...)` is lost the next time the container auto-resolves the class for ThrottleRequests middleware. Look for this pattern wherever the absence of a provider meets instance-state-holding classes. Cross-cuts the "no provider" pattern (broken at C05, continues into C06): a missing provider is structurally NOT just a missing binding — it's also a missing singleton lifecycle, with knock-on instance-state-loss bugs.
- NEW pattern (C06): **inputs-from-Phalcon-input-bag instead of authenticated user.** `ThrottleRequests::resolveMaxAttempts` reads `$request->get('authenticated_user')['rate_limit']`; `resolveRequestSignature` reads `$request->get('user')`. `$request->get(...)` is Phalcon's GET∪POST input bag, NOT Laravel's `Request::user()` auth model. Effect: a POST-body field LITERALLY named `authenticated_user` becomes the source-of-truth for per-user rate-limits — trivially client-spoofable AND unreachable from the actual Auth\Manager. Distinct from C01's silent-arg-drop (`$remember` ignored): here the API LOOKS auth-aware but reads the WRONG SURFACE. Watch this shape in any code that "looks for the current user" without going through `app('auth')->user()` or `$request->user()`. Pattern note: Phare\Http\Request still lacks a user() method (US-A04), so any middleware/limiter that wants the user has only the input bag — flag for US-S01 as an **architectural cascade defect** (gap upstream forces wrong surface downstream).
- NEW silent-arg-drop instance (C06): `RateLimiter::hit($key, $decaySeconds=60)` is hardcoded to amount=1 — drops Laravel's `$amount` param entirely. Running silent-arg-drop list is now 6 instances across 4 areas: B02 `update($values)`, B03 BelongsToMany attach `$touch`, C01 attempt|login|loginUsingId `$remember`, C03 createBcryptDriver/createArgonDriver config dropthrough, C05 VerifyCsrfToken `$encrypter`, **C06 hit `$amount`**. Plus a related stub-defect-family instance: `Phare\RateLimit\Limit::response($callback)` setter exists but `Middleware\ThrottleRequests::handleRequest` reads it NOWHERE — promote to defect-list entry. The stub-defect family is now 9 instances (A04 Request::route, A05 Response::view, A06 validator exists/unique, A07 View::render, B01 castAttribute custom-cast branch, B03 Relation::getRelationExistenceQuery, B05 Migrator::runDown error-swallow, C03 silent-config-dropthrough, C06 Limit::response).
- NEW pattern (C06): **hardcoded HTTP status code inside Exception ctor** is now a 2-instance recurring pattern, not a one-off. C05 `TokenMismatchException` `$code = 419`. C06 `TooManyRequestsException::__construct(...) { parent::__construct($message, 429, $previous); }`. Watch for this in C07 (PasswordReset throwing 422/410?), D01 (Queue MaxAttemptsExceededException?), E04 (CommandNotFoundException 127?). The fix shape is shared: extend Symfony's `HttpException` / `*HttpException` and inherit the code from the framework boundary, never hardcode in the exception class itself. Add to US-S01 §1 inventory.

## 2026-05-19 - US-A05 Audit Response
- Diffed Phare response surface vs Laravel 13 Http/{Response,ResponseTrait,JsonResponse,RedirectResponse}.php + Routing/ResponseFactory.php (+ contract).

NO JsonResponse, NO RedirectResponse, NO ResponseFactory.
- **Learnings for future iterations:**

  - `FileResponse`/`StreamedResponse` extend `Phalcon\Http\Response` directly (not Phare's `Response`) — a subsystem can have classes that bypass the project's own wrapper. Check the `extends` clause of every class, not just the primary one.
