# Ralph Progress — Laravel 13 Parity Audit Pass

## Codebase Patterns
- Audit PRD is READ-AND-RECORD ONLY. Never edit any file under `src/Phare/`. Output is docs only.
- Laravel 13 reference is read-only at `/opt/laravel-framework/src/Illuminate/` — confirmed version `13.2.0` (const VERSION in Foundation/Application.php).
- Each subsystem story appends a `### <Subsystem>` section to `docs/audit-area-{a..e}.md` in the fixed shape: `Current` / `Expected` / `Gaps` / `Effort: S|M|L`.
- Gaps split into three categories: Missing / Type mismatch / Phalcon leak.
- Wrapper Rule (§2): a public method param/return of raw `Phalcon\*` type = a leak/gap. Container `get()/has()` inherited from `Phalcon\Di\Di` is a pre-documented exception, NOT a new gap.
- Effort rating is coarse S/M/L with a one-line rationale.
- Enumerate Laravel public methods fast: `grep -oE 'public function [a-zA-Z_]+\(' <file>` (avoid piping into RTK-hooked commands that choke on `--` flags; keep grep simple).
- Phare public APIs are frequently UNTYPED (no param/return types) — record that as a Type mismatch vs Laravel's typed signatures.
- The Ralph runner expects `tasks/prd.json`; it was generated from `tasks/prd-parity-audit-pass.md`. Branch: `ralph/parity-audit-pass`.

  - `docs/audit-area-a.md` now has a header block; future Area-A stories should APPEND their `### <Subsystem>` section, not recreate the file.
  - Check `src/Phare/Contracts/` for the interface that defines a subsystem's intended public surface — useful for the Current column.

## 2026-05-19 - US-A04 Audit Request
- Diffed Phare `Http\Request` public API vs Laravel 13 `Http/Request.php` + `Concerns/InteractsWithInput.php` (which composes `Support/Traits/InteractsWithData.php`).
- Files changed: docs/audit-area-a.md (### Request section), tasks/prd.json, tasks/progress.txt. No framework code touched.
- Result: Effort L. Phare `Request` extends `\Phalcon\Http\Request` (class-level leak — whole Phalcon API published) and the contract `Contracts\Http\Request extends Phalcon\Http\RequestInterface` (leak baked into published contract). Request is structurally a validation object: ctor takes `$rules`, `make()`/`validate()` are a validation harness. `validate()` returns bool not the validated array; `getMessages()` is a single-error flat array not a MessageBag. `route()` is a stub returning null. ~50+ Laravel methods missing (input-shape helpers, URL/path API, content negotiation, flash, precognition, ArrayAccess/Macroable).
- **Learnings for future iterations:**
  - Laravel 13 moved the input-shape helpers (`has/filled/only/except/string/enum/collect/whenHas/...`) into `Support/Traits/InteractsWithData.php`, pulled in via `InteractsWithInput`. Grep that trait too — `InteractsWithInput` alone only shows ~15 methods.
  - Phare `Request`'s `input()` reads a construct-time snapshot `$this->data = $this->get()` (Phalcon GET∪POST) — it never sees the JSON body. Real correctness bug, not just a parity gap.
  - `### Request`'s validation surface (`$validators`, `make`, `validate`, `rules`) overlaps US-A06 (FormRequest + Validation) — flag the decoupling there, don't double-count effort.
  - Pattern confirmed: Phalcon leaks here are STRUCTURAL (extends a Phalcon class / contract extends a Phalcon interface), not signature-level — Phare's own method signatures carry no `Phalcon\*` types. Distinguish the two leak forms in the audit.

## 2026-05-19 - US-A05 Audit Response
- Diffed Phare response surface vs Laravel 13 Http/{Response,ResponseTrait,JsonResponse,RedirectResponse}.php + Routing/ResponseFactory.php (+ contract).
- Files changed: docs/audit-area-a.md (### Response section), tasks/prd.json, tasks/progress.txt. No framework code touched.
- Result: Effort L. Phare = `Http\Response` (extends `Phalcon\Http\Response`, implements contract that extends `Phalcon\Http\ResponseInterface`) + unbound `FileResponse`/`StreamedResponse` (extend `Phalcon\Http\Response` directly) + `response()`/`redirect()` helpers. NO JsonResponse, NO RedirectResponse, NO ResponseFactory.
- **Learnings for future iterations:**
  - Response leaks on ALL THREE axes simultaneously: class inheritance (`extends Phalcon\Http\Response`), contract extension (`Contracts\Http\Response extends Phalcon\Http\ResponseInterface`), AND signature-level (`redirect()/back()/redirectTo()` return raw `Phalcon\Http\ResponseInterface`). Earlier sections each had only 1-2 of these — Response is the worst case so far.
  - `Response::status(int): static` is a SETTER returning `$this`; Laravel's `ResponseTrait::status(): int` is a GETTER. Same name, opposite semantics — record as a Type-mismatch porting hazard, not just a missing method.
  - `Response::view()` is a literal stub: sets content to `"View: <name> with data: <json>"`. Treat such "would need integration"/debug-string stubs as correctness defects in the audit, separate from parity gaps (same pattern as Request's `route()` stub in US-A04).
  - Laravel's `response()` with no args returns the ResponseFactory, not a Response — the factory is the real response API (17 verbs incl. noContent/jsonp/eventStream/streamJson/redirectToRoute/...). Phare's `response()` always returns a Response. When auditing a "factory" subsystem, diff the *factory contract*, not just the value classes.
  - `FileResponse`/`StreamedResponse` extend `Phalcon\Http\Response` directly (not Phare's `Response`) — a subsystem can have classes that bypass the project's own wrapper. Check the `extends` clause of every class, not just the primary one.

## 2026-05-19 - US-A07 Audit View / Blade
- Diffed Phare view + Blade surface vs Laravel 13 View/Factory.php, View/Compilers/BladeCompiler.php + 21 Concerns/Compiles*.php, ComponentTagCompiler, Concerns/Manages*.
- Files changed: docs/audit-area-a.md (### View / Blade section), tasks/prd.json, tasks/progress.txt. No framework code touched.
- Result: Effort L. Phare ships TWO conflicting view stacks. Engine is vendored EFTEC/BladeOne v4.9 — ~98 compile* methods vs Laravel 13's 124; ~30 directives missing.
- **Learnings for future iterations:**
  - Phare has NO Blade compiler of its own. `Phare\View\Blade extends BladeOne` — `BladeOne.php` is a vendored 3rd-party single-file engine (EFTEC/BladeOne v4.9, ~4160 lines). Directive parity = whatever BladeOne ships, not Phare-authored.
  - TWO providers bind `'view'`: `View\ViewServiceProvider` (→ `Phare\View\Factory`, modern, but `View::render()` is a debug-string STUB — non-functional) AND `Providers\BladeViewProvider` (→ `Phare\View\BladeView extends Phalcon\Mvc\View`, functional, renders via a Phalcon `dispatch:afterExecuteRoute` event). Whichever registers last wins. Check BOTH `src/Phare/View/` and `src/Phare/Providers/` for a subsystem — providers can live outside the subsystem dir.
  - Stub-defect pattern continues 4x: `Request::route()` (A04), `Response::view()` (A05), validator `exists`/`unique` no-op (A06), now `View::render()` (A07). When auditing, always open the primary `render()`/main method body — a Laravel-shaped class can be a hollow stub.
  - Enumerate BladeOne directives: `grep -hoE 'function compile[A-Z][a-zA-Z]+' BladeOne.php` (do NOT pipe into `sed`/`sort` in one line — the RTK grep hook hijacks multi-stage pipes; run grep alone, dedupe by eye or a second call).
  - Laravel 13 Blade directive count = `grep -rhoE 'protected function compile[A-Z][a-zA-Z]+' BladeCompiler.php Concerns/*.php | sort -u | wc -l` → 124. Run from inside `View/Compilers/`.
  - Phalcon leak split mirrors A04/A05: structural class-level (`BladeView extends Phalcon\Mvc\View`) + provider coupling (`BladeViewProvider implements Phalcon\Di\ServiceProviderInterface`). The modern stack (`Factory`/`View`/`ViewComposer`/`TemplateEngine`) and `BladeOne` itself are Phalcon-CLEAN.
  - No `Phare\Contracts\View\*` namespace exists — view layer publishes no interface.
